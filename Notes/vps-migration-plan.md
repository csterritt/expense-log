# Migration Plan: Cloudflare Worker + D1 → Stand-alone Process on a VPS

> Scope: This is a planning document only. No code has been changed. It lists
> every Cloudflare-specific dependency in the project, the recommended
> replacement, the concrete edits, and the steps for provisioning, data
> migration and cutover.

---

## 1. Summary of recommended target

| Concern            | Today (Cloudflare)                                  | Target (VPS)                                                         |
| ------------------ | --------------------------------------------------- | -------------------------------------------------------------------- |
| Runtime            | workerd, `export default { fetch, scheduled }`      | Node 24 (matches `.node-version`) + `@hono/node-server`              |
| Database           | D1 (`PROJECT_DB` binding, `drizzle-orm/d1`)         | SQLite file via `@libsql/client` + `drizzle-orm/libsql`              |
| Config / secrets   | `wrangler.jsonc` vars, `.dev.vars`, `cloudflare:workers` `env` | `process.env`, loaded from an `.env` file (`node --env-file`) / systemd `EnvironmentFile` |
| Static assets      | Workers Assets (`./public`, served before the Worker) | `serveStatic` from `@hono/node-server` (or the reverse proxy)       |
| Cron               | `triggers.crons: ["0 5 * * *"]` → `scheduled()`     | systemd timer (or in-process scheduler) calling the same logic       |
| Build              | `wrangler build` / `wrangler deploy` (esbuild inside) | `esbuild` bundle → `dist/server.js`, `dist/cron.js`                |
| TLS / edge         | Cloudflare edge                                     | Caddy (auto-HTTPS) reverse proxy → `127.0.0.1:3000`                  |
| Logs               | `observability`, `wrangler tail`                    | stdout → journald (`journalctl -u expense-log -f`)                   |
| Schema changes     | `wrangler d1 execute … --file`                      | `sqlite3 <db> < schema.sql` (or drizzle migrator)                    |

### Why these choices

- **Node over Bun**: `package.json` declares `engines.node >= 22` and
  `.node-version` pins 24.19; Hono, Better Auth, nodemailer, and
  `crypto.subtle` all work natively. (Bun is a viable alternative — it runs
  TSX directly and needs no build step — see §9.)
- **libsql over better-sqlite3 / bun:sqlite**: the code relies heavily on
  `db.batch([...])` (≈15 call sites in `src/lib/db/*.ts`) for atomic
  multi-statement writes. In the installed `drizzle-orm@0.45.4`, only the
  `d1` and `libsql` drivers implement `batch()`. libsql is also async (like
  D1), so no call site needs to change shape. better-sqlite3 would require a
  shim like the one in `tests/helpers/test-db.ts`.
- **SQLite file over Postgres**: D1 *is* SQLite, so schema, migrations in
  `drizzle/`, `schema-prod.sql`, and every query port unchanged. The app is a
  single-user/small-group tool; one process with one SQLite file is ample.

### Important consequence: run exactly ONE process

SQLite, Better Auth's default in-memory rate limiter, and
`emailRateLimitCache` (`src/routes/auth/handle-forgot-password.ts:47`) all
assume a single process. Do **not** use PM2 cluster mode or multiple
replicas. (This is actually *more* consistent than Workers, where those maps
were per-isolate.)

## 2. Inventory of Cloudflare-specific code

### 2.1 Entry point — `src/index.ts`

- L5 `import { env } from 'cloudflare:workers'` — used at module load for
  `validateEnvironmentVariables()`, `isTestRouteEnabled(...)`, and the
  `SIGN_UP_MODE` route-registration branch (L187–207).
- L72–74 require `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_DATABASE_ID`,
  `CLOUDFLARE_D1_TOKEN` — these are only used by `drizzle.config.ts`, not the
  app, and must be removed from the required list.
- L163–169 per-request middleware `createDbClient(c.env.PROJECT_DB)`.
- L238 `export default { fetch: app.fetch, scheduled }`.

### 2.2 Database client & types

- `src/db/client.ts` — `drizzle-orm/d1`, takes a `D1Database`.
- `src/types.d.ts` — `DrizzleD1Database` in `ContextVariableMap`.
- `src/local-types.ts:28` — `Bindings.PROJECT_DB: D1Database`; also
  `CLOUDFLARE_*` fields (L32–34).
- `worker-configuration.d.ts` — generated by `wrangler types`; supplies the
  global `D1Database`, `ScheduledEvent`, `ExecutionContext` types.

### 2.3 Direct uses of `c.env.PROJECT_DB` (≈44 sites)

Every route re-creates a client with `createDbClient(c.env.PROJECT_DB)`
even though middleware already puts one in `c.get('db')`:

- `src/routes/build-categories.tsx` (5), `build-tags.tsx` (5),
  `build-summary.tsx` (1), `build-recurring.tsx` (1)
- `src/routes/expenses/build-edit-expense.tsx` (5), `expense-get-handler.ts`,
  `expense-post-handler.ts`, `expense-confirm-post-handler.ts` (1 each)
- `src/routes/recurring/build-create-recurring.tsx` (3),
  `build-edit-recurring.tsx` (5)
- `src/routes/auth/handle-forgot-password.ts`, `handle-resend-email.ts`,
  `handle-sign-up.ts` (1 each); `src/lib/sign-up-utils.ts` (1)
- `src/routes/test/database.ts` (10), `src/routes/test/run-cron.ts` (1)
  (these two also type their router as `Bindings: { PROJECT_DB: D1Database }`)
- `src/lib/auth.ts:24` — `createAuth(env)` builds its own client from
  `env.PROJECT_DB`; called with `c.env` from ~12 places.
- `src/scheduled.ts:15,27` — `dbFactory(env.PROJECT_DB)`.

### 2.4 D1-specific result / error shapes

- `src/lib/db/auth-access.ts:129,162` — `result.meta?.changes` (D1 shape).
  libsql returns `{ rowsAffected }`. **These would silently become `0`**,
  breaking gated sign-up code claiming/releasing. L264–266 already has a
  `rowsAffected` fallback — apply the same pattern (or a small
  `affectedRows(result)` helper) to all three.
- `src/lib/db/auth-access.ts:193–213` — `isUniqueConstraintError` already
  matches `SQLITE_CONSTRAINT_UNIQUE` / `UNIQUE CONSTRAINT`, which libsql
  emits. Keep; the `D1_ERROR` branch becomes dead but harmless.
- `db.batch(...)` in `expense-access.ts`, `tag-access.ts`,
  `category-access.ts` — supported by libsql (runs in a transaction, same
  atomicity as D1). No change.

### 2.5 Behavioural differences between D1 and plain SQLite

- **Foreign keys**: D1 enforces FKs by default; plain SQLite does **not**.
  The schema relies on `ON DELETE CASCADE` (account/session/submissionKey →
  user, expenseTag/recurringTag) and `RESTRICT` (category/tag). Must run
  `PRAGMA foreign_keys = ON` on the connection at startup.
- **Concurrency**: set `PRAGMA journal_mode = WAL` and
  `PRAGMA busy_timeout = 5000`.
- **Retries**: `withRetry` (`src/lib/db-helpers.ts`) was tuned for D1
  network blips. Keep it; local SQLite errors are rarely transient, so
  retries mostly just add latency on genuine constraint errors — acceptable.

### 2.6 Scheduled handler — `src/scheduled.ts`

Signature is `(event: ScheduledEvent, env: Bindings, ctx: ExecutionContext)`
and both `event`/`ctx` are unused. Wrangler fires it at `0 5 * * *` **UTC**.
`tests/scheduled.spec.ts` constructs fake `ScheduledEvent`/`ExecutionContext`.

### 2.7 Static assets

`wrangler.jsonc` `assets` serves `./public` with `run_worker_first: false`,
so files in `public/` (including `public/index.html` at `/`, the
timestamped `style-*.css`, and `public/js/*`) are served **before** any Hono
middleware runs (no CSRF, secure headers, body limit, logging on them).
`buildRoot` (`/`) is `PRODUCTION:REMOVE`, so in production `/` *is*
`public/index.html`.

### 2.8 Origins / cookies / proxy

- `src/lib/origin-config.ts:18,26` — `CANONICAL_ORIGIN =
  'https://expenses.cls.cloud'` and `'https://expense-log.cleverfox.workers.dev'`.
  Remove the `workers.dev` origin after cutover; change the canonical one if
  the domain changes.
- Better Auth resolves client IP from `x-forwarded-for` by default
  (`@better-auth/core/dist/utils/ip.mjs`). Cloudflare set this; on the VPS the
  reverse proxy must set it, and `advanced.ipAddress` should be configured
  (see §4.6).
- `secure: true // PRODUCTION:UNCOMMENT` cookies (`src/constants.ts:109`)
  continue to work because Caddy terminates HTTPS.

### 2.9 Things that already work on Node (no change)

- Email: production path is a `fetch` POST to `EMAIL_SEND_URL`
  (`src/lib/email-service.ts:103–129`); dev/test path uses nodemailer to
  mailpit. Both fine on Node.
- `crypto.subtle` (`src/lib/confirmation-hmac.ts`) — global in Node 24.
- `process.env.NODE_ENV` (`src/lib/logger.ts:20`), `process.argv`
  (`email-service.ts:44`).
- Pushover (`src/lib/po-notify.ts`) — `fetch`.
- `Intl`-based ET date logic (`src/lib/et-date.ts`) — Node ships full ICU.
- Module-level test state (clock override, SMTP override, DB-failure
  cookies) — now shared process-wide instead of per-isolate; fine for tests.

### 2.10 Tooling & scripts

| File                       | Cloudflare dependency                               |
| -------------------------- | --------------------------------------------------- |
| `package.json`             | `build`, `deploy`, `cf-typegen` scripts; `wrangler` devDep |
| `wrangler.jsonc`           | everything                                          |
| `worker-configuration.d.ts`| generated Worker types                              |
| `drizzle.config.ts`        | `driver: 'd1-http'` + `CLOUDFLARE_*` creds          |
| `run-dev.sh`               | builds `.dev.vars`, runs `wrangler dev`             |
| `build-schema-update.sh`   | `wrangler d1 execute … [--remote]`                  |
| `try-reload-db.sh`         | hard-codes `.wrangler/state/v3/d1/...sqlite`        |
| `watch-logs.sh`            | `wrangler tail`                                     |
| `.dev.vars.all.template`   | `CLOUDFLARE_*` vars                                 |
| `README.md`                | D1/wrangler setup instructions                      |
| `.gitignore`               | `.wrangler`, `.dev.vars`                            |

## 3. Phase 1 — Platform-neutral refactors (can ship to Cloudflare first)

These changes reduce the later diff and can be deployed and verified on the
existing Worker before anything moves.

1. **Use the request-scoped client everywhere.** Replace all ≈44
   `createDbClient(c.env.PROJECT_DB)` with `c.get('db')`. Retype the two test
   routers (`test/database.ts`, `test/run-cron.ts`) as `Hono<AppEnv>`.
2. **Decouple `createAuth` from the binding.** Change to
   `createAuth(env: Bindings, db: DrizzleClient)` and update callers to pass
   `c.get('db')`.
3. **Normalise affected-row counts.** Add a helper in `src/lib/db-helpers.ts`:
   `affectedRows = (r) => r?.meta?.changes ?? r?.rowsAffected ?? 0` and use it
   in `auth-access.ts` (3 sites). Add unit tests for `claimSingleUseCode` /
   `releaseSingleUseCode` returning `true` on success (currently untested
   against a non-D1 driver).
4. **Simplify the scheduled signature.** Extract
   `runDailyJob(env: Bindings, db: DrizzleClient)` from `createScheduled`;
   keep a thin Worker adapter `scheduled(_event, env) => runDailyJob(env,
   createDbClient(env.PROJECT_DB))`. Update `tests/scheduled.spec.ts` to test
   `runDailyJob` directly.
5. **Drop `CLOUDFLARE_*` from `validateEnvironmentVariables`** in
   `src/index.ts` (they are build-tool credentials, not runtime config).

Run `bun test` and the full Playwright suite; deploy to Cloudflare.

## 4. Phase 2 — Node runtime

### 4.1 Dependencies

- Add: `@hono/node-server`, `@libsql/client`, `esbuild` (dev). Optionally
  `tsx` (dev) for a watch-mode dev server.
- Remove (at the end): `wrangler`.
- Follow the repo's pinned-version style and prefer releases ≥ 7 days old.

### 4.2 Database client — `src/db/client.ts`

```ts
import { createClient } from '@libsql/client'
import { drizzle } from 'drizzle-orm/libsql'
import * as schema from './schema'

export const openDatabase = async (url: string) => {
  const client = createClient({ url }) // e.g. file:/var/lib/expense-log/expense-log.db
  await client.execute('PRAGMA foreign_keys = ON')
  await client.execute('PRAGMA journal_mode = WAL')
  await client.execute('PRAGMA busy_timeout = 5000')
  return drizzle(client, { schema })
}
```

Open it **once** at startup; the per-request middleware in `index.ts` just
does `c.set('db', db)`.

- `src/types.d.ts`: `DrizzleD1Database` → `LibSQLDatabase<typeof schema>`
  (or simply `DrizzleClient` from `local-types.ts`).
- `src/local-types.ts`: remove `PROJECT_DB` and `CLOUDFLARE_*`; add
  `DATABASE_URL`, `PORT`, `HOST`. Update the "Cloudflare Worker environment
  bindings" doc comment.

### 4.3 Configuration — replace `cloudflare:workers`

- Create `src/config.ts` that reads `process.env` into a typed `Bindings`
  object once.
- In `src/index.ts`, replace `import { env } from 'cloudflare:workers'` with
  that object. Turn the module into `export const createApp = (env:
  Bindings, db: DrizzleClient) => { ... return app }` so the route-registration
  branch on `SIGN_UP_MODE` still runs at construction time.
- Keep `c.env` working for the ~15 places that read it (`c.env.SIGN_UP_MODE`,
  `createAuth(c.env)`, `pushoverNotifyEnv(c.env)`, `isOriginAllowed(c.env)`,
  `validateEnvBindings`…) by passing the bindings into every request:
  `serve({ fetch: (req) => app.fetch(req, env) })`. With
  `@hono/node-server`, `c.env` would otherwise be `{ incoming, outgoing }`.

### 4.4 New entry point — `src/server.ts`

```ts
import { serve } from '@hono/node-server'
import { loadConfig } from './config'
import { openDatabase } from './db/client'
import { createApp } from './index'

const env = loadConfig()
const db = await openDatabase(env.DATABASE_URL)
const app = createApp(env, db)
const server = serve({
  fetch: (req) => app.fetch(req, env),
  port: Number(env.PORT ?? 3000),
  hostname: env.HOST ?? '127.0.0.1',
})
const shutdown = () => server.close(() => process.exit(0))
process.on('SIGTERM', shutdown)
process.on('SIGINT', shutdown)
```

Bind to `127.0.0.1` in production so only the reverse proxy can reach it.

### 4.5 Static assets

Register **before** all other middleware in `createApp`, to preserve the
current "assets first" behaviour:

```ts
import { serveStatic } from '@hono/node-server/serve-static'
app.use('*', serveStatic({ root: './public' }))  // also serves / → index.html
```

Add `Cache-Control: public, max-age=31536000, immutable` for
`/style-*.css` (filename is timestamped by `timestamp-build-filenames.js`)
and a short max-age for `/js/*`. Alternatively let Caddy serve `public/`
directly (`file_server`) and only proxy misses — either is fine; doing it in
Hono keeps dev and prod identical.

### 4.6 Better Auth behind a proxy — `src/lib/auth.ts`

```ts
advanced: {
  ipAddress: { ipAddressHeaders: ['x-forwarded-for'] },
},
```

Caddy sets `X-Forwarded-For` by default. Also consider creating the
`betterAuth` instance once (it is currently rebuilt on each `createAuth`
call) — optional, now cheap to do since `db` is a singleton.

### 4.7 Cron — replace `triggers.crons`

Recommended: a separate short-lived entry `src/cron.ts` run by a systemd
timer, so a crash in the job cannot affect the web process and missed runs
are caught up (`Persistent=true`):

```ts
const env = loadConfig()
const db = await openDatabase(env.DATABASE_URL)
await runDailyJob(env, db)
```

```ini
# /etc/systemd/system/expense-log-cron.timer
[Timer]
OnCalendar=*-*-* 05:00:00 UTC
Persistent=true
[Install]
WantedBy=timers.target
```

`materializeRecurring` is idempotent (unique index
`expense_recurring_occurrence_unique`), so a catch-up run is safe.
Alternative: an in-process scheduler (e.g. `croner`) in `server.ts`
— fewer moving parts but no catch-up after downtime.

The `/test/run-cron` route keeps working unchanged after Phase 1.

### 4.8 Build

- `package.json` scripts:
  - `"build": "esbuild src/server.ts src/cron.ts --bundle --platform=node --format=esm --target=node24 --packages=external --jsx=automatic --jsx-import-source=hono/jsx --outdir=dist"`
  - `"start": "node --env-file=.env dist/server.js"`
  - `"cron": "node --env-file=.env dist/cron.js"`
  - `"dev": "tsx watch --env-file=.env src/server.ts"` (used by `run-dev.sh`)
  - remove `deploy` (wrangler) and `cf-typegen`.
- `tsconfig.json`: already `types: ["node"]`; delete
  `worker-configuration.d.ts` and fix any remaining `D1Database` /
  `ScheduledEvent` / `ExecutionContext` references.
- `clean-for-production.rb` / `PRODUCTION:*` markers are runtime-agnostic and
  continue to work; run it before `npm run build` as today.

## 6. Phase 4 — VPS provisioning

### 6.1 Host

- Any small Linux VM (1 vCPU / 1 GB is plenty). Ubuntu/Debian LTS.
- Firewall: allow 22, 80, 443 only.
- Install Node 24.19 (via `fnm`/`nvm` or NodeSource), `sqlite3`, Caddy.
- Create system user `expense-log`; app in `/opt/expense-log`, data in
  `/var/lib/expense-log` (owner `expense-log`, mode 700), secrets in
  `/etc/expense-log/env` (mode 600).

### 6.2 systemd service

```ini
# /etc/systemd/system/expense-log.service
[Service]
User=expense-log
WorkingDirectory=/opt/expense-log
EnvironmentFile=/etc/expense-log/env
ExecStart=/usr/bin/node dist/server.js
Restart=on-failure
NoNewPrivileges=true
ProtectSystem=strict
ReadWritePaths=/var/lib/expense-log
[Install]
WantedBy=multi-user.target
```

Plus `expense-log-cron.service` (`Type=oneshot`, `ExecStart=/usr/bin/node
dist/cron.js`, same user/env) and the timer from §4.7.

Production env file: `NODE_ENV=production`, `DATABASE_URL`,
`BETTER_AUTH_SECRET`, `SIGN_UP_MODE`, `EMAIL_SEND_URL`, `EMAIL_SEND_CODE`,
`PO_APP_ID`, `PO_USER_ID`, `ALTERNATE_ORIGIN`, `PORT`, `HOST`. Copy values
from the Worker's secrets (`wrangler secret list` shows names only — values
come from your own records / `.dev.vars.all`). **Never** set
`ENABLE_TEST_ROUTES` in production (and the `PRODUCTION:REMOVE` build strips
them anyway).

### 6.3 Caddy

```
expenses.cls.cloud {
  encode zstd gzip
  request_body { max_size 8KB }
  reverse_proxy 127.0.0.1:3000
}
```

Caddy provides TLS (Let's Encrypt), HTTP/2/3, and `X-Forwarded-For`.
You lose Cloudflare's edge DDoS/WAF; if you want it back, keep the domain
proxied through Cloudflare DNS (orange cloud) pointing at the VPS, and then
use `cf-connecting-ip` in `ipAddressHeaders` and restrict 443 to Cloudflare
IP ranges.

### 6.4 Backups & monitoring

- Nightly `sqlite3 expense-log.db ".backup /var/backups/expense-log/$(date +%F).db"`
  via a timer, rotated, and copied off-box (or use Litestream for continuous
  replication to S3/R2/B2).
- Uptime check on `https://expenses.cls.cloud/auth/sign-in`.
- The cron job already reports failures via Pushover; consider also
  alerting when `expense-log-cron.service` fails (`OnFailure=`).

## 7. Phase 5 — Data migration & cutover

1. **Dry run**: on the VPS with a copy of production data:
   ```sh
   wrangler d1 export pl-exp-log-db --remote --output=d1-dump.sql
   sqlite3 /var/lib/expense-log/expense-log.db < d1-dump.sql
   sqlite3 /var/lib/expense-log/expense-log.db 'PRAGMA foreign_keys=ON; PRAGMA foreign_key_check; PRAGMA integrity_check;'
   ```
   Drop any `_cf_*` / `d1_migrations` tables if present. Compare row counts
   per table against D1 (`wrangler d1 execute … --remote --command "SELECT
   count(*) FROM …"`). Note timestamps are stored as integers and port
   byte-for-byte.
2. Start the service, point a hosts-file entry (or the `ALTERNATE_ORIGIN`
   hostname) at the VPS, and smoke-test: sign in, list/add/edit/delete an
   expense, summary, recurring CRUD, password reset email, and a manual
   `systemctl start expense-log-cron`.
3. **Cutover** (expect a few minutes of downtime):
   1. Lower DNS TTL a day ahead.
   2. Stop writes on Cloudflare (e.g. `wrangler deploy` a maintenance
      Worker, or just pick a quiet time — it's a personal app).
   3. Disable the Worker cron trigger so recurring expenses aren't generated
      twice (idempotency would prevent duplicates on the *same* DB, but the
      two DBs are now separate).
   4. Fresh `wrangler d1 export` → import → checks from step 1.
   5. Switch DNS for `expenses.cls.cloud` to the VPS.
   6. Users will need to sign in again only if sessions weren't migrated —
      they are (the `session` table is in the dump), and
      `BETTER_AUTH_SECRET` must be identical, so sessions should survive.
4. **Rollback**: keep the Worker and D1 intact for ~2 weeks. Rollback = DNS
   back to Cloudflare (data written on the VPS in the interim would need to
   be re-imported into D1 manually).

## 8. Phase 6 — Decommission Cloudflare

After the rollback window:

- Remove `wrangler.jsonc`, `worker-configuration.d.ts`, the `wrangler`
  devDependency, the Worker `scheduled` adapter, the `workers.dev` entry in
  `STATIC_TRUSTED_ORIGINS`, and the `D1_ERROR` branch in
  `isUniqueConstraintError`.
- Take a final D1 export for the archive, then delete the Worker and the
  `pl-exp-log-db` database.

## 9. Alternative: Bun runtime

If you'd rather avoid a build step: Bun runs `src/server.ts` (TSX included)
directly, and the unit tests already use Bun. Differences from the plan
above:

- Use `Bun.serve({ fetch: (req) => app.fetch(req, env), port })` and
  `serveStatic` from `hono/bun`.
- Keep `@libsql/client` + `drizzle-orm/libsql` (works under Bun) for
  `batch()` support — `drizzle-orm/bun-sqlite` has no `batch()`.
- `ExecStart=/usr/local/bin/bun src/server.ts`; no esbuild.
- Trade-off: `.node-version`/`engines` would no longer describe production,
  and nodemailer/Better Auth are better-trodden on Node.

## 10. Risk checklist

| Risk | Mitigation |
