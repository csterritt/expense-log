# PRD: Expense Log 2 — Duplicate Expense Detection

## Problem Statement

Users sometimes record the same expense twice. They might enter it, forget, and enter it again a few days later, or someone else may log a spend that was already recorded (all data is shared between signed-in users). Today the app accepts every valid submission without question, so these duplicates quietly inflate the list and every summary total. Nothing in the app points out that a new entry looks like one that already exists, and the only fix is to notice the problem by eye later and delete the extra row by hand.

Duplicates are rarely exact. The second entry often has a slightly different description ("Grocery store" vs "Grocery store trip"), a slightly different amount ($100.00 vs $100.50), or a date a few days off. An exact-match check would miss most of them.

## Solution

When the feature is complete:

- When a signed-in user submits a **new expense** that closely matches one or more existing expenses (similar description, similar amount, dates within 7 days of each other), the app saves nothing yet. It shows a **duplicate check page** that lists every matching existing expense and offers four choices:
  - **Replace existing**: overwrite a chosen existing expense with the new values. No new row is created.
  - **Discard new**: keep the existing expense(s) and throw away the new submission.
  - **Keep both**: save the new expense as normal.
  - **Back to form**: return to the entry form with every value still filled in, saving nothing.
- When a signed-in user **edits** an expense so that it closely matches another existing expense, the app shows a **duplicate warning page** that lists the matches and offers **Save anyway** or **Cancel** (back to the edit form with values preserved). No merging happens on edit.
- Exact matches (identical description, amount, and date) count as duplicates too.
- Matching runs across **all** expenses in the app, consistent with the shared-data model.
- If the submission also creates new categories or tags, the duplicate check comes **first**. The existing "create new category/tags" confirmation follows only if the user chooses Keep both or Replace.
- Expenses generated by recurring templates are never checked when the cron inserts them. They can still show up as *candidates* when a user enters a matching manual expense.

## User Stories

### Detection on create

1. As a signed-in user, when I submit a new expense that closely matches an existing one, I want to be told before anything is saved, so that I don't record the same spend twice.
2. As a signed-in user, I want an expense to count as a potential duplicate only when all three conditions hold (similar description, similar amount, and a date within 7 days), so that I am not nagged about unrelated expenses.
3. As a signed-in user, I want an exact match (same description, amount, and date) to be flagged as well, so that the most obvious double entry is caught.
4. As a signed-in user, I want amounts to count as similar when they differ by no more than $1.00 or 1% of the larger amount, whichever is greater, so that both small and large expenses are matched sensibly.
5. As a signed-in user, I want descriptions to count as similar when one's words contain the other's, when they share at least half their words, or when they differ only by small typos, so that "Grocery store", "Grocery store trip" and "Grocry store" all match each other.
6. As a signed-in user, I want letter case, extra whitespace and punctuation ignored when comparing descriptions, so that "Grocery Store." and "grocery store" match.
7. As a signed-in user, I want category and tags ignored when matching, so that a duplicate entered under a different category is still caught.
8. As a signed-in user, I want matching to consider every expense in the app (not just ones I entered), so that duplicates entered by another user are caught.
9. As a signed-in user, I want expenses generated by recurring templates to be eligible as candidates, so that I don't manually re-enter a bill the cron already recorded.
10. As a signed-in user, when my new expense matches nothing, I want the save to behave exactly as it does today, with no extra page, so that normal entry stays fast.

### Duplicate check page (create)

11. As a signed-in user, I want the duplicate check page to show the expense I'm trying to add (date, description, category, tags, amount), so that I can compare it to the existing ones.
12. As a signed-in user, I want every matching existing expense listed with its date, description, category, tags, formatted amount, and the recurring badge if it was generated, so that I can judge each match.
13. As a signed-in user, I want candidates ordered with exact matches first and then from closest to least close, so that the most likely duplicate is at the top.
14. As a signed-in user, I want to choose **Replace existing** and pick which candidate to replace (when there is more than one), so that I can correct an earlier entry with the new values.
15. As a signed-in user, when I choose Replace, I want the chosen existing expense to take the new description, amount, date, category and tags while keeping its identity (and its recurring link, if any), so that its history and recurring provenance are preserved and no extra row is created.
16. As a signed-in user, I want to choose **Discard new** and be returned to the list with a message confirming nothing was added, so that I can move on.
17. As a signed-in user, I want to choose **Keep both** and have the new expense saved normally, so that legitimately similar expenses (e.g. two coffees in one week) can still be recorded.
18. As a signed-in user, I want a **Back to form** option that returns me to the entry form with every value (including tag chips, new-tag text and new-category text) preserved and nothing saved, so that I can adjust the entry.
19. As a signed-in user, if I choose Replace with more than one candidate but don't pick one, I want a clear error on the duplicate check page, so that nothing is replaced by guesswork.
20. As a signed-in user, after Replace or Keep both succeeds, I want to be redirected to the list with a success message, so that I can see the result.

### Interaction with new category / tag confirmation

21. As a signed-in user, when my submission both matches an existing expense and introduces new categories or tags, I want the duplicate check first, so that I'm not asked to create names for an expense I end up discarding.
22. As a signed-in user, if I choose Discard new or Back to form on the duplicate check page, I want no categories or tags created, so that no orphaned names are left behind.
23. As a signed-in user, if I choose Keep both or Replace and my submission introduces new names, I want the existing new-items confirmation page to follow, showing the new names and my duplicate choice, so that I confirm everything before anything is written.
24. As a signed-in user, when I confirm on the new-items page after choosing Replace, I want the new categories/tags to be created and the existing expense overwritten together in one atomic step, so that a failure leaves nothing half-done.
25. As a signed-in user, if I cancel on the new-items page, I want to return to the entry form with all values preserved and nothing saved, consistent with today's behaviour.
26. As a signed-in user, I don't want the duplicate check to run again after I've already answered it for this submission, so that I'm never stuck in a loop.

### Detection on edit

27. As a signed-in user, when I save an edit and the edited expense closely matches another existing expense, I want a warning page listing the matches, so that I notice I may be creating or keeping a duplicate.
28. As a signed-in user, I want the expense I'm editing excluded from its own candidate list, so that it never matches itself.
29. As a signed-in user, I want the warning to appear on every edit save that produces matches (even when I only changed tags), so that the behaviour is predictable.
30. As a signed-in user, I want the warning page to offer **Save anyway** (save the edit as normal) and **Cancel** (return to the edit form with all values preserved, nothing saved), so that I keep control.
31. As a signed-in user, when an edit both matches another expense and introduces new categories/tags, I want the duplicate warning first and the existing new-items confirmation after Save anyway, consistent with create.
32. As a signed-in user, I don't want any merge or replace option on edit, so that editing stays simple.

### Failure modes and races

33. As a signed-in user, if the candidate I chose to replace has been deleted or changed by someone else since the duplicate check page was shown, I want to be returned to the entry form with a clear recoverable error and all values preserved, with nothing written, so that I never overwrite data I didn't see.
34. As a signed-in user, if the duplicate lookup itself fails (database error), I want the standard "Failed to save expense. Please try again." error with my values preserved, and nothing saved, so that a failed check is never treated as "no duplicates".
35. As a signed-in user, if someone tampers with the hidden fields on the duplicate check or warning page (changes the amount, or swaps the target id for one that was never offered), I want the submission rejected with a recoverable error, so that only the choices I was shown can take effect.
36. As a signed-in user, if my submission is invalid (validation error), I want the normal field-level errors shown immediately without any duplicate check, so that validation always comes first.
37. As a signed-in user, if a background retry replays my duplicate-page choice (Replace, Keep both, Discard), I don't want it applied twice, so that resilient submission stays idempotent.
38. As a signed-in user with JavaScript disabled, I want the duplicate check page, the warning page and all of their choices to work as plain server-rendered forms, so that the feature degrades gracefully.
39. As an unauthenticated visitor, I want every new duplicate-related route to redirect me to sign-in, so that data is never exposed.

### Non-triggers

40. As a signed-in user, I want the nightly recurring cron to insert generated expenses without any duplicate check, so that scheduled entries are never blocked waiting for a human.
41. As a signed-in user, I don't want a background scan or report of existing duplicates in this release, so that scope stays focused on preventing new ones.

## Implementation Decisions

### Matching rules (owned entirely by the Duplicate Matcher)

All three conditions must hold for an existing expense to be a candidate:

- **Date**: `|proposed.date − existing.date| ≤ 7` calendar days, inclusive (a 15-day span centred on the proposed date). Dates are `YYYY-MM-DD` strings, and the difference is calendar-day arithmetic with no timezone conversion.
- **Amount**: `|a − b| ≤ max(100, ceil(0.01 × max(a, b)))` in integer cents. (Examples: $100.00 vs $101.00 match; $100.00 vs $101.01 do not; $500.00 vs $504.99 match.)
- **Description**: both descriptions are first normalized: lowercase, every run of non-alphanumeric characters replaced by a single space, then trimmed. They are similar if **either** test passes:
  - **Token overlap**: split the normalized strings into word sets. They match if either non-empty set is a subset of the other, or if the Jaccard index (|A ∩ B| / |A ∪ B|) is ≥ 0.5.
  - **Edit distance**: normalized Levenshtein similarity `1 − distance / max(lenA, lenB)` is ≥ 0.7.
- **Exact match**: normalized descriptions are equal, amounts are equal, and dates are equal. Exact matches are always candidates.
- Category and tags are **not** considered.
- Thresholds (7 days, $1.00, 1%, Jaccard 0.5, Levenshtein 0.7) are named constants inside the matcher. They are not user-configurable and not environment-configurable. They are expected to be tuned, so they must be easy to find and change in one place.

### Ranking

Candidates are ordered as follows: exact matches first, then by smallest absolute date difference, then by smallest absolute amount difference, then by highest description similarity score, then by expense id for a stable order. All candidates are shown. The 7-day window naturally bounds the list.

### Where detection runs

- **Create** (the primary expense POST): after field validation and tag/category input validation succeed, and **before** the new-items confirmation. If there are candidates, render the duplicate check page. If not, continue exactly as today.
- **Edit** (the expense update POST): same position. Candidates exclude the expense being edited. The check runs on every save, whatever fields changed.
- **Not** run by the recurring cron, the recurring template forms, or any category/tag management action.
- **Not** run again on the submit coming from the duplicate check/warning page, or on the new-items confirmation submit that follows it. The user's decision is carried forward instead (see *Signed payload*).

### Duplicate check page (create) — choices and effects

- **Replace existing** (requires a `targetId` from the offered candidates; a radio selection, pre-selected when there is exactly one candidate): overwrite the target expense's `description`, `amountCents`, `date`, `categoryId` and full tag set with the submitted values. `id`, `createdAt`, `recurringId` and `occurrenceDate` are preserved, and `updatedAt` is bumped. Because `occurrenceDate` is preserved, the recurring dedupe index still prevents the cron from re-inserting that occurrence.
- **Discard new**: no write. Redirect to the list with a flash message ("Expense not added — existing expense kept.").
- **Keep both**: proceed with the normal create path (direct insert, or the new-items confirmation if new names are present).
- **Back to form**: redirect to the entry form with all values preserved via the existing form-state mechanism, and no error.
- If new categories/tags are present and the user chose Replace or Keep both, render the existing new-items confirmation page. It additionally displays and carries the duplicate decision (`keep-both` or `replace:<targetId>`). Its confirm handler performs category/tag creation plus either the insert or the overwrite in a **single transaction**.

### Duplicate warning page (edit) — choices and effects

- **Save anyway**: proceed with the normal edit path (direct update, or the new-items confirmation if new names are present).
- **Cancel**: redirect to the edit form for that expense with all submitted values preserved.

### Signed payload and tamper protection

- The duplicate check and warning pages extend the existing confirmation-HMAC mechanism. The signed payload covers the submitted expense fields (as today) plus the offered candidate list as `(id, updatedAt)` pairs, plus, on edit, the id of the expense being edited.
- The handler verifies the signature before anything else. A `targetId` that is not among the signed candidates is rejected as tampering (recoverable error, values preserved).
- When the duplicate decision is carried into the new-items confirmation page, that page's signed payload also covers the decision and, for Replace, the target's `(id, updatedAt)`.

### Concurrency (optimistic check on Replace)

- The overwrite runs in one transaction and succeeds only if the target row still exists **and** its `updatedAt` equals the value captured when the duplicate check page was rendered. Otherwise the result is a recoverable `target-changed` / `target-missing` error. The user is redirected to the entry form with a clear message and all values preserved. Nothing is written, including any new categories/tags in the combined case.
- Keep both and Discard have no target and need no concurrency check. Changes to other candidates after the page was rendered are ignored.

### Idempotency

- Replace and Keep both commit through the existing atomic idempotency ledger using the form's `submissionKey`, with outcomes equivalent to today's "expense added" outcome. Replace has its own outcome message ("Existing expense updated.").
- Discard and Back to form perform no write and need no ledger entry, since replaying them is harmless.
- The `submissionKey` from the original form render is carried unchanged through the duplicate page and the new-items page.

### Error handling and logging

- Failures in the duplicate lookup query are infrastructure errors: the user sees the standard save-failed message with values preserved, and the route plus error class are logged. They are never treated as "no candidates".
- Logging discipline is unchanged: no descriptions, amounts, names or raw bodies are logged.

### Schema changes

- **None required.** The existing `expense.updatedAt` serves as the optimistic-concurrency token.
- An index on `expense(date)` is recommended to keep the ±7-day window query cheap. If added, it comes with a Drizzle migration.

### Routes

- New POST route for the duplicate check page decision on create (sibling of the existing confirm-create-new route).
- New POST route for the duplicate warning decision on edit (sibling of the existing edit-confirm route).
- Both routes are behind the existing signed-in access middleware, and both forms carry a `submissionKey` and are progressively enhanced by resilient-submit like every other mutation form.

## Module Design

- **Duplicate Matcher**
  - **Responsibility**: Decide which existing expenses are potential duplicates of a proposed expense, and rank them. It owns normalization, all thresholds, both description-similarity algorithms, the amount tolerance, the date window, exact-match detection and ranking. It is pure, with no DB or time coupling.
  - **Interface**: `findDuplicateCandidates(proposed: { description; amountCents; date }, existing: ExpenseLike[]) → RankedCandidate[]`. Each result carries the original row plus `isExact`, `dayDiff`, `amountDiffCents` and `descriptionScore`. Also exports the window size (days) so the data-access layer can prefilter. It never fails: invalid input is a caller bug, because inputs have already been validated.
  - **Stability**: thresholds and algorithm are expected to change. The function signature is stable.
  - **Tested**: yes

- **Duplicate candidate lookup (expense data access)**
  - **Responsibility**: Fetch the full display rows (with category name, tags, recurring marker and `updatedAt`) of every expense whose date falls within the matcher's window around a given date, optionally excluding one expense id. Then run the matcher and return ranked candidates with display data.
  - **Interface**: `findDuplicateCandidatesFor(db, proposed, { excludeId? }) → Result<RankedCandidateRow[], DbError>`.
  - **Tested**: yes

- **Expense overwrite (expense data access)**
  - **Responsibility**: Atomically overwrite an existing expense's fields and tag set with optimistic concurrency, optionally creating new categories/tags in the same transaction, and recording the idempotency key.
  - **Interface**: `replaceExpense(db, { targetId, expectedUpdatedAt, description, amountCents, date, existingCategoryId | newCategoryName, existingTagIds, newTagNames }, submission) → Result<Expense, 'target-missing' | 'target-changed' | ConflictError | DbError>`. Preserves `id`, `createdAt`, `recurringId` and `occurrenceDate`. Reuses the existing confirmation-time race handling for names created concurrently.
  - **Tested**: yes

- **Duplicate check page and decision handler (create)**
  - **Responsibility**: Render the duplicate check page (proposed expense, ranked candidates, four choices), verify the signed payload, and dispatch the chosen action: overwrite, discard, insert, back to form, or hand off to the new-items confirmation carrying the decision.
  - **Interface**: an HTTP POST handler plus a render function, following the existing `renderConfirmNewItems` style. Failure modes: tamper (recoverable), missing target selection (re-render with error), target changed/missing (back to form with error), DB error (standard error).
  - **Tested**: yes (handler unit tests and e2e)

- **Duplicate warning page and decision handler (edit)**
  - **Responsibility**: Render the warning page for edits and dispatch Save anyway (normal update, or new-items confirmation) or Cancel (back to the edit form).
  - **Interface**: an HTTP POST handler plus a render function. Failure modes: tamper (recoverable), DB error (standard error).
  - **Tested**: yes (handler unit tests and e2e)

- **Changes to existing modules**
  - Expense create and edit POST handlers: call the candidate lookup after validation, and branch to the duplicate page when there are candidates.
  - New-items confirmation page and confirm handlers: accept, display, sign and honour a carried duplicate decision (`keep-both` | `replace:<id>@<updatedAt>`). Skip re-running detection.
  - Confirmation HMAC: extend the signed payload shape to cover the candidate list, the decision and the edited-expense id.
  - **Stability**: the prompt UI and the set of choices may evolve, so keep rendering separate from decision dispatch.

## Testing Decisions

- Tests check external behaviour (which expenses are flagged, what ends up in the database, where the user lands, what is preserved), not internal structure.
- **Duplicate Matcher unit tests**: table-driven boundary cases for each rule: day diff 7 vs 8, across month and year boundaries; amount at exactly $1.00 and $1.01 apart for small amounts, and exactly 1% vs just over 1% for large amounts, including rounding at the `ceil` edge; description containment, Jaccard exactly 0.5 vs below, Levenshtein exactly 0.7 vs below, case/punctuation/whitespace normalization, empty-after-normalization descriptions; exact matches; a pair that passes two rules but fails the third is *not* a candidate; ranking order and tie-breaks.
- **Data-access tests** (in the style of the existing expense-access spec, against the test DB helper): window prefilter includes ±7 days and excludes ±8; `excludeId` honoured; candidates include recurring-generated rows with their marker; `replaceExpense` overwrites fields and tags while preserving `id`/`createdAt`/`recurringId`/`occurrenceDate`; it fails with `target-missing` / `target-changed` and writes nothing (including no new categories/tags) in those cases; the idempotency ledger prevents a double apply.
- **Handler unit tests** (in the style of the existing expense-confirm and recurring-confirm handler specs): no candidates leads to the unchanged create/edit path; candidates lead to the duplicate page being rendered; each create choice (Replace with one/many candidates, missing selection, Discard, Keep both, Back) with and without new names; edit Save anyway / Cancel; tampered amount; `targetId` not offered; target changed/deleted between steps; DB error in the lookup; replayed `submissionKey`; detection not re-run on the decision or new-items submits.
- **E2E tests** (Playwright, following the numbering and helpers in the existing `e2e-tests/expenses/` suite): create a near-duplicate and exercise each of the four choices; multiple candidates with Replace picking a specific one; duplicate plus new category/tag, sequenced correctly, with Discard creating no names; edit warning Save anyway / Cancel; a recurring-generated candidate shows its badge and is preserved as recurring after Replace; the no-JS path for the duplicate page; resilient-submit replay of a Replace does not double-apply.

## Out of Scope

- Duplicate checks during recurring cron materialization, or any deferred "review later" queue.
- Duplicate checks on recurring template create/edit.
- A scan, report or page that finds duplicates already in the database.
- Remembering "Keep both" decisions. Pairs may be flagged again on later edits, and no acknowledgement table is added.
- Replace or merge options on the edit warning page.
- Using category or tags as matching signals.
- User- or environment-configurable thresholds.
- Restricting matching to the current user's expenses, or adding expense ownership columns.
- Client-side (as-you-type) duplicate hints. Detection happens on submit only.
- Bulk delete or bulk merge of duplicates.

## Open Questions

- **Threshold tuning**: the initial constants (7 days, max($1, 1%), Jaccard 0.5, Levenshtein 0.7) are educated guesses. *Owner*: Chris. *Resolution*: use the feature for a few weeks and adjust the constants in the matcher if false positives or misses are noticeable.
- **`expense(date)` index**: whether the list's existing data volume justifies a new index. *Owner*: implementer. *Resolution*: check the query plan for the window query; add the index and migration if it does a full scan.

## Further Notes

- The existing confirmation-page conventions are reused, not reinvented: consolidated confirmation, HMAC-signed hidden payload, full revalidation on submit, cancel/back preserving all values, atomic transactions and the idempotency ledger.
- The existing auth, sign-up, recurring and resilient-submit e2e tests must continue to pass unchanged. In particular, all current expense-entry e2e tests use data that must not accidentally trigger the duplicate page. Where seed data would trigger it, the test should be updated deliberately, not silently.
- Follow the project's `// PRODUCTION:REMOVE` / `// PRODUCTION:UNCOMMENT` conventions for any test hooks, and kebab-case `name-action` `data-testid` values (e.g. `duplicate-replace`, `duplicate-discard`, `duplicate-keep-both`, `duplicate-back`, `duplicate-save-anyway`, `duplicate-cancel`).
